# Why Parla

Most i18n bugs are type bugs. A key that doesn't exist, a param nobody passed, a namespace read
before it loaded: each renders a blank or a raw key, and each is something TypeScript could catch.
Parla keeps what runs and what type-checks aligned.

## The reasons

- **`t` is proof of loading.** `useParla([checkout])` returns a `t` holding only the namespaces that
  loaded; reading another is a type error, not a blank string. Namespaces are imported objects, so
  the types and the bundle follow the same imports.
- **Params come from the message.** A plural needs its number, each branch of a select types its own
  params, and each rich-text tag takes a callback whose node type follows the instance: `ReactNode`
  with `@parlajs/react`, `string` with `@parlajs/core`.
- **One way to call each thing.** `parla.load([…])` and `useParla([…])` always take a list, so
  tooling such as [x18n](/reference/x18n) has one shape to read.
- **No flash on switch.** `setLocale` loads the new locale first, then switches.
- **ICU and MessageFormat 2**, per namespace, through one data model.
- **No locale data to ship.** Formatting uses `Intl`; on Hermes (React Native), add its polyfills.
- **Monorepos.** Each namespace has one owner package, which apps import.

## Why it was built

To keep runtime behaviour and type checking aligned. Elsewhere, reading a namespace that hasn't
loaded type-checks and renders a blank. Each library above gets part of this right; none makes the
types and the runtime agree on keys, params and loading at once. Parla does, at 2.7 kB.

None of these ideas is new on its own: Parla combines them, and the
[launch post](/blog/introducing-parla) credits where each comes from.

Parla is built with the help of AI coding tools.
